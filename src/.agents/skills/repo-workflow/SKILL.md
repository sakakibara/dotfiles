# Repo workflow

Applies to the user's published repos (as the global instructions define them). Every landing goes through a `ci/` branch whose CI run passed on the exact commit; a repo whose `ci.yml` does not yet run on `ci/**` is brought in by its first landing (step 0). Other repos follow their own flow.

The guarantee: the tip of every branch that releases - main, and `published-compatibility`'s lines, series branches, and version branches - is always a commit whose `ci-ok` passed on every platform the project claims, holding signed commits in a linear history; every release tag points at such a commit. CI tests only the tip of each landing, so a tip whose CI failed never lands, and commits below the tip are untested; tags are verified per commit, never inferred from a branch's history. GitHub accepts any verified signature (its own and Dependabot's included), so the `%G?` check in step 3 is what shows that each commit the user made or recreated carries the user's key; a contributor's commit landed unchanged carries GitHub's verification of its own signer.

Every outward step needs the user's yes. The landing yes is the one combined yes allowed; it lapses when the session ends. Landing needs GitHub credentials: inside agent-sandbox, queue it for the host session. Every landing waits for a full CI run, documentation fixes included; that is the price of a branch that releases never being red.

## Landing

The target is a branch that releases: main, or a line, series branch, or version branch. A landing pushes the commit to `ci/<topic>` on origin, `<topic>` being the local topic branch's name; `ci/` branches have no consumers, are created once, and are deleted after the landing.

0. Bring-in: if the target's `ci.yml` lacks the `ci/**` push trigger or the `ci-ok` job of "CI workflow", the landing's first commit on that target adds both (renaming a CI workflow with another name, such as `test.yml`, to `ci.yml`, and removing every README badge for it: main gets no runs of its own, so the badge would show a stale result). A push runs the `ci.yml` in the pushed commit, so that commit's own run tests it, and it lands through the steps below like any other. A line or series branch is brought in the same way before its first backport, in the same landing yes, and its bring-in commit also installs the release workflow's verification ("Releases"), since a tag runs the tagged commit's own release workflow. A `ci/` branch left from an earlier landing is proposed for deletion, each deletion with its own yes. A repo with no CI: propose adding it; until the user agrees, push the target directly after the local checks, each push with its own yes.
1. Work on a local topic branch, one per change; local main only mirrors origin main (fast-forward it when origin moves, never commit on it). Run the local checks: formatter and linter, the full test suite, shell tests under the OS's own `/bin/bash`. Then commit (signed) on the topic branch. For committing, these are the verification; CI on other platforms gates landing, not committing.
2. Rebase the agent's own unpushed commits onto the target's tip (`git fetch origin`), or onto the PR head when landing a PR unchanged. Pin committer dates and compare every field as the history-rewrite rule requires. Where the project wants every commit green, land one commit per landing.
3. Ask for the landing yes. Show the target, `git log --format='%h %G? %an | %cn %s%n%b' origin/<target>..<sha>` (bodies included, so every `Fixes`, `Refs`, and cross-repository reference is seen: a `Fixes` line closes its issue when the target moves), and any change to `.github/` (any workflow's `permissions:` included), to the build's test step, or to a script CI runs. Every commit must be `G`, except in a PR landed unchanged: there fetch `refs/pull/<n>/head` as `<PR head>`, which must equal `headRefOid` and be an ancestor of `<sha>`; the commits in `origin/<target>..<PR head>` must equal the PR's commits in order (`git rev-list --reverse` against `gh pr view <n> --json commits`) and pass the mechanical checks of "Landing unchanged" (ancestry, no merge commit, each verified); and every commit in `<PR head>..<sha>` must be `G`. Chain all of these with `&&`; otherwise stop. Confirm its message and naming conditions by reading the log shown. For a PR that will show Merged, also show its description's closing keywords and linked issues (`gh pr view <n> --json body,closingIssuesReferences`): GitHub closes those issues when it marks the PR merged. The yes covers pushing that SHA to `ci/<topic>`, one rerun of a setup failure, fast-forwarding the target to that SHA when `ci-ok` passes (or creating it there, for a new release branch the yes names), and deleting `ci/<topic>`, and any earlier `ci/` branch the yes names as replaced, afterwards. Rebasing again or adding a commit needs a new yes.
4. `git push --force-with-lease=ci/<topic>: origin <sha>:refs/heads/ci/<topic>`: the empty lease makes the push create the branch and fail if it already exists. A rebased or fixed commit goes to a new name (`ci/<topic>-2`), and the old one is named in the new yes and deleted with it; a `ci/` branch is never force-pushed. A push runs the pushed commit's workflows in the base repo, with its secrets and whatever `permissions:` those files request (the default read-only token does not cap an explicit request): for a PR, a commit that changes `.github/` or a script a workflow runs is pushed only after the user has read that diff and the yes names it.
5. Find the run (`gh run list --commit <sha> --branch ci/<topic> --event push --workflow ci.yml --json databaseId,status,conclusion`), polling at most 5 minutes; a `pull_request` run tests a merge ref, not the SHA, and never counts; if none appears, report the cause (a skip marker such as `[skip ci]` in the tip's message, a disabled workflow, an outage) and stop. Never land a commit whose message holds a skip marker. Wait with `gh run watch <id> --exit-status` (every job sets `timeout-minutes`, which bounds the wait), then decide by that run's `ci-ok`: `gh run view <id> --json jobs --jq '.jobs[] | select(.name == "ci-ok") | .conclusion'`.
6. `success`: `git push origin <sha>:refs/heads/<target>`. A non-fast-forward rejection means the target moved: restart at step 2 with a new yes. Confirm `origin/<target>` is the SHA, then delete `ci/<topic>` (`git push --force-with-lease=ci/<topic>:<sha> origin :refs/heads/ci/<topic>`). Fast-forward the local target branch to the SHA and delete the local topic branch.
7. Anything else: read the jobs. A failed setup step (toolchain or tool install, checkout) or a lost runner gets one `gh run rerun <id> --failed`, then step 5 again. A failed build or test step is real: fix it, amend the fix into the commit that broke it (pinning dates, comparing fields; for a contributor's commit, as "Contributor and Dependabot PRs" says, and in a landing that kept them unchanged, a fix in your own commit on top keeps it unchanged only while the contributor commits still pass the local checks; otherwise switch to "Rebasing"), and restart at step 1 with a new yes. A cancelled job is reported, not retried silently. The target never moves until `ci-ok` passes.

Never use GitHub's merge buttons: they bypass the `ci/` branch's run, rebase-merge leaves commits unverified, and squash and merge commits carry GitHub's signature. Never create a commit status or check run by hand.

## Landing several targets at once

One fix for several targets (a backport, or a security fix at disclosure): one landing yes may name every target and SHA. Push them in one `git push`, each to `ci/<topic>` of its own local topic branch, with one create-only lease per branch as in step 4 (`git push --force-with-lease=ci/<t1>: --force-with-lease=ci/<t2>: origin <a>:refs/heads/ci/<t1> <b>:refs/heads/ci/<t2>`), so their CI runs in parallel, and fast-forward each target as its own `ci-ok` passes; a failure on one does not hold the others.

## Creating a release branch

A new line, series branch, or version branch (published-compatibility): where the repo has a branch ruleset, first confirm it targets the new name (`gh api 'repos/{owner}/{repo}/rules/branches/<name>'` lists the `ci-ok` check and the signed-commits, linear-history, non-fast-forward, and deletion rules); if it does not, extend the ruleset's targets with the user's yes and verify again before creating the branch. Ask for the branch and its landing together, naming both. Make its first commit on the base - `ci.yml` to the current standard with the branch's toolchain pinned, and the release workflow with the verification below (not for a version branch, which has no tags) - and land it with the base in place of `origin/<target>`; the push in step 6 creates the branch at a commit whose `ci-ok` passed. Step 3's signature checks are the gate there: a ruleset's signature check does not run at creation.

## The rulesets

The branch and tag rulesets are optional hardening, applied only when the user wants them, after main exists, with no bypass actors; the merge-method and workflow-token settings below are always applied. Applying, changing, or temporarily disabling one (for example, for a commit the user chose to leave unsigned) is a security setting needing the user's yes each time.

- Branches (a backstop: its required `ci-ok` is also satisfied by a `pull_request` run on the PR head, so step 5 stays the gate): targets the default branch and every pattern of branches that release (`zig-*`, `v*.x`, the project's version-branch names), never `ci/**`. Require status check `ci-ok` from GitHub Actions (`integration_id` 15368), with `do_not_enforce_on_create: false` and `strict_required_status_checks_policy: false` set explicitly; require linear history; require signed commits; block force pushes; restrict deletions.
- Tags: targets `v*`. Require status check `ci-ok` from GitHub Actions, with `do_not_enforce_on_create: false`; restrict updates and deletions.
- Merge methods: merge commits and squash merging disabled (`gh api -X PATCH 'repos/{owner}/{repo}' -F allow_merge_commit=false -F allow_squash_merge=false`), leaving only rebase merging, which the signed-commits rule rejects where the branch ruleset is applied (without it, only "Never use GitHub's merge buttons" prevents a merge-button landing); a squash merge is GitHub-signed and linear, so the rulesets alone would let a merge button land a PR tested only against the base its PR CI saw.
- Workflow token: the repo's default workflow permissions are read-only and workflows cannot approve pull requests (`gh api -X PUT 'repos/{owner}/{repo}/actions/permissions/workflow' -f default_workflow_permissions=read -F can_approve_pull_request_reviews=false`). The app pin on `ci-ok` excludes statuses set by people and other apps; it cannot stop a workflow holding a write token from creating a passing `ci-ok` and a verified commit itself, which the read-only token and the CI workflow's `permissions:` prevent.

Verify read-only: where the rulesets are applied, `gh api 'repos/{owner}/{repo}/rulesets/{id}'` shows `enforcement: active`, `bypass_actors: []`, `current_user_can_bypass: never`, the targets above, and the check with its `integration_id` and both flags; `gh api 'repos/{owner}/{repo}/actions/permissions/workflow'` shows `read` and `false`; `gh api 'repos/{owner}/{repo}' --jq '[.allow_merge_commit, .allow_squash_merge]'` shows `[false,false]`. Before requiring signatures, confirm the current tip shows `.commit.verification.verified == true`. Where applied, the first landing tests the branch ruleset. The tag ruleset is tested once, in a scratch repository with the same rulesets and no release workflow, using the tag kind releases use (annotated and signed): a tag on an untested commit is rejected, one on a landed commit is accepted; the scratch repository is deleted afterwards, each step with the user's yes.

## CI workflow

- `.github/workflows/ci.yml` runs `on: push: branches: ['ci/**']` and `pull_request`, so main and release branches get no run of their own: the run that counts is the `ci/` branch's. No `paths:` filter. It sets `permissions: {}` at the top and gives each job only what it reads (`contents: read`; `ci-ok` adds `actions: read`); no workflow that runs on `ci/**` or `pull_request` grants any write permission. No workflow uses `pull_request_target`, or a `workflow_run` that checks out or runs PR code: both run with the base repo's privileges. Every job sets `timeout-minutes`. Scheduled, fuzz, docs-deploy, and benchmark jobs live in other workflows.
- Every job runs on every push; nothing is skipped, and no job uses `continue-on-error`. Every job is in `ci-ok`'s `needs`, so `ci-ok` starts after all of them.
- The final job, the only check landing reads, checks every other job of the run as of its latest attempt, so a job missing from `needs` or skipped by a partial rerun still fails it:

  ```yaml
  ci-ok:
    if: always()
    needs: [lint, test, cross]
    runs-on: ubuntu-latest
    timeout-minutes: 5
    permissions: {actions: read}
    steps:
      - shell: bash
        env: {GH_TOKEN: "${{ github.token }}"}
        run: |
          set -o pipefail
          gh api "repos/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID/jobs?filter=all&per_page=100" --paginate --jq '.jobs[]' \
            | jq -rs '[.[] | select(.name != "ci-ok")] | group_by(.name) | map(max_by(.run_attempt).conclusion) | unique[]' > c
          [ "$(cat c)" = success ] || { echo "jobs ended:"; cat c; exit 1; }
  ```

  `if: always()` exactly, since with `!cancelled()` a cancelled run skips `ci-ok` and a skipped check counts as success.
- Concurrency: `group: ci-${{ github.ref }}`, `cancel-in-progress: true`.
- Toolchain: every version `published-compatibility` requires CI to test (the range's oldest and newest on a compatible toolchain; a breaking toolchain's one toolchain series, each line its own), pinned and cached, from the official source; a mirror download is verified with minisign against the pinned Zig key, and an unverified download fails the job.
- Matrix: every platform the project claims - Linux x64 and arm64, macOS arm64, Windows x64 - plus cross builds for 32-bit, big-endian, wasm, and Windows arm64 where the language allows; shell code also under macOS's `/bin/bash`. The README claims nothing CI does not test.
- `.gitattributes` `* text=auto eol=lf` (check `git ls-files --eol` first where CRLF fixtures are intentional).
- Actions pinned by full commit SHA with a version comment (`uses: actions/checkout@<sha> # v5`): this forgoes Dependabot's security alerts for Actions, which cover only version-tag refs, in exchange for refs nobody can move; Dependabot version updates keep them current.

## Releases

Tag only a commit already on main or a line or series branch (a version branch has no tags; landing on it is its release). Before tagging, check `git merge-base --is-ancestor <sha> origin/<branch>` and that the `ci-ok` of the SHA's push run (Landing, step 5) is `success`. The release workflow repeats both before publishing anything (a `pull_request` run's check on the same SHA would satisfy a check-runs query, so it reads the push run):

```yaml
permissions: {contents: write, actions: read}
steps:
  - uses: actions/checkout@<sha> # v5
    with: {fetch-depth: 0}
  - env: {GH_TOKEN: "${{ github.token }}"}
    run: |
      b=$(git branch -r --contains "$GITHUB_SHA" --format='%(refname:lstrip=3)' | grep -Ex 'main|zig-[0-9]+\.[0-9]+|v[0-9]+(\.[0-9]+)?\.x' || true)
      [ -n "$b" ] || { echo "tag is on no branch that releases"; exit 1; }
      id=$(gh run list -R "$GITHUB_REPOSITORY" --commit "$GITHUB_SHA" --event push --workflow ci.yml --json databaseId --jq '.[0].databaseId')
      c=$(gh run view "$id" -R "$GITHUB_REPOSITORY" --json jobs --jq '.jobs[] | select(.name == "ci-ok") | .conclusion')
      [ "$c" = success ] || { echo "ci-ok of the push run: $c"; exit 1; }
```

It also fails unless the tag is `v<major>.<minor>.<patch>` and equals the version in the project's manifest (`build.zig.zon`, `Cargo.toml`, ...). Adjust the branch pattern to the project's release branches. This replaces re-running the test matrix on the tag.

The release body is that version's CHANGELOG section (carrying every release-notes item `published-compatibility` requires), or without a CHANGELOG notes written to the same headings; never GitHub's generated notes. A project shipping binaries creates the release as a draft, uploads every asset with a `SHA256SUMS` (which its installer verifies, where it has one), then publishes; propose enabling immutable releases for it (a security setting), so published assets cannot be replaced.

## Contributor and Dependabot PRs

CI runs on the PR (its `ci-ok` there does not count for landing). Review with `review-pull-request`; a PR that is spam, unrelated to the project, or generated without understanding of it gets a short close proposal instead. PR-controlled code stays untrusted through landing: its builds and tests, the local checks of step 1 included, run only in the isolated environment `review-pull-request` requires (none available: stop and ask). Only committing, signing, and pushing run on the host, in a checkout whose git hooks run no repo-tracked code.

- **Who changes what.** Ask the contributor, in the review, for changes to design, behavior, or tests. Make the rest yourself at landing: a rebase over a moved base, conflicts, toolchain or CI bumps the change needs, formatting, the commit message in the repo's convention, and the CHANGELOG entry (in your own commit right after theirs; the commit's author credits the contributor, so the entry names no one). When a PR has waited on its author for 30 days after your latest request (no push, no reply; a reply promising the work restarts the count once), propose to the user finishing it yourself or closing it as not planned with an invitation to reopen.
- **Landing unchanged.** Land the PR's commits as they are - SHAs, authors, and signatures kept, your own changes following as your commits on top, and GitHub marking the PR Merged once its head reaches the target - when all of these hold: they sit on the target's tip (`git merge-base --is-ancestor origin/<target> <PR head>`) with no merge commit (`git rev-list --merges origin/<target>..<PR head>` prints nothing); each is verified on GitHub (`gh api 'repos/{owner}/{repo}/commits/<sha>' --jq .commit.verification.verified`), whether or not a ruleset enforces it; none needs a reword, amend, or squash (the repo's message convention, a `!` for a break, a skip marker, a failing local check); and none names the user as author, committer, or in a trailer. Locally such a commit may show any `%G?` value; GitHub's verification decides.
- **Rebasing.** Otherwise rebase the contributor's commits onto the target (`git rebase --force-rebase origin/<target>`, which also recreates commits already on the tip). The rebased commits are new commits you make, so they carry the user's signature as committer: author fields stay, and committer name, email, and date change (the landing's own date) - compare every other field. A commit naming the user as author or in a trailer is landed neither way: ask the contributor to fix it, and report it to the user. Make your own commits on top afterwards, so none of yours is rewritten; if the base moves again, rebase only the contributor commits and recreate yours, or pin each of yours to its own `%cI`. If the PR comes from a fork's branch other than its default branch and allows maintainer edits (`gh pr view <n> --json isCrossRepository,headRepositoryOwner,headRepository,headRefName,maintainerCanModify`), ask with the landing yes for a separate yes to push the rebased contributor commits there, so the PR shows Merged: after `ci-ok` passes and before step 6, `git push --force-with-lease=<branch>:<old head> https://github.com/<fork owner>/<fork repo>.git <last rebased contributor commit>:refs/heads/<branch>` (the lease is the check that the contributor has not pushed since). If that push is rejected, do not retry or force it: continue with step 6, and the PR shows Closed. If step 6 is then rejected, the restart needs a new fork-push yes as well. Otherwise the PR shows Closed.
- **Authorship.** The contributor stays author of what they wrote. Your changes go in separate commits, or, where a contributor commit fails the local checks without them, are amended into the commit they repair (`git commit --amend -F <msg>` keeps its author). Squash contributor commits only when they cannot each be made to pass the local checks; the squashed commit keeps the PR author's authorship (`git reset --soft <base>`, then `git commit -C <the PR author's earliest commit>`, then amend the message), and every other author gets `Co-authored-by:`. A commit holding your code beyond rebasing and rewording adds `Co-authored-by:` for the user, as `git config user.name` and `user.email` print in that repo. The user becomes author, with the contributor as `Co-authored-by:`, only when the contributor's code survives in the landed change only as lines anyone making the same change would write identically (an API rename the toolchain forces). A contributor's co-author line uses their commit's address when GitHub links it to their account (`gh api 'repos/{owner}/{repo}/commits/<sha>' --jq .author.login` is not null), otherwise, for the PR author, `<id>+<login>@users.noreply.github.com` (`gh api users/<login> --jq .id`), and for any other author the address on their commit. A PR from another of the user's own accounts keeps its author fields, with no thanks, praise, or co-author line. The landing yes names the method (unchanged, or rebase with any amends or squashes) and each landed commit's author.
- **Closing.** Post the closing comment, with the user's yes: it links the landed commits and says plainly what landed unchanged and what changed, and why. If GitHub has not marked the PR Merged, confirm its head is still the commit you landed or rebased, then close it, with the user's yes.
- **Dependabot PRs** are reviewed like any PR and wait on no one: one that is behind gets a `@dependabot rebase` comment (with the user's yes) and then lands as "Landing unchanged" or "Rebasing" decides; make any needed change yourself in a separate commit on top, and close the PR with a one-line comment linking the commit unless GitHub marked it Merged or Dependabot closed it. `dependabot.yml` groups each ecosystem's updates into one PR per repo, monthly.

**Issues and replies.** Reply within 7 days to every person (not Dependabot or another bot) who opened an issue or PR the user has not answered, or whose latest comment or push, on any issue or PR whoever opened it, came after the user's last comment there and asks something of the user or answers the user's request; draft it, and post with the user's yes. Triage each new issue: a bug report missing the version or a minimal reproduction gets a request for them; a feature request is the user's decision (draft a recommendation with its reason; never promise); a question is answered and closed as completed; a duplicate is closed as duplicate, linking the original; one belonging to another repo of the same account is proposed for issue transfer (another account's: reply with a link and close as not planned). An issue waiting on its author for 30 days after the latest request is proposed for closing as not planned with an invitation to reopen. Close as completed only what was fixed or answered, as not planned what was declined or could not be reproduced. A commit that does not close its issue (`Refs`, a subject-only repo, a fix on another branch): reply naming where the fix is and which branches still wait for a backport, and propose closing the issue once the last covered branch lands. A fix reply names its release once published, or says it will be in the next release, without a date. No stale bot. Never argue with a hostile or abusive participant: propose hiding the comment, locking the conversation, a temporary interaction limit, or blocking the participant. Each close, lock, hide, limit, block, or transfer needs the user's yes.

## Bringing a repo in

A new published repo starts with all of it; an existing one is brought in once, one step at a time, each with the user's yes: the read-only workflow token; `ci.yml` with `ci-ok` on main and on every existing line and branch, each installed by its first landing (Landing, step 0); `.gitattributes`; the release workflow's verification on main and every line and series branch; README Compatibility; `SECURITY.md` and private vulnerability reporting; secret scanning with push protection; Dependabot (version updates for Actions and the repo's Go, Rust, or npm ecosystem; alerts and security updates); the merge methods; watch with all activity; then, if the user wants them, the rulesets, last, verified as above. Do the first repo end to end before the rest. Afterwards verify read-only: `gh api 'repos/{owner}/{repo}' --jq .security_and_analysis` (secret scanning and push protection enabled; Dependabot security updates enabled where Dependabot supports an ecosystem the repo uses), `gh api 'repos/{owner}/{repo}/private-vulnerability-reporting'` enabled, `gh api 'repos/{owner}/{repo}/vulnerability-alerts'` succeeding (alerts on), `dependabot.yml` present, the merge methods and, where applied, the rulesets as above, and the subscription `subscribed`.

Each account that owns published repos has a public `.github` repository, created with the user's yes, holding default community files that every repo without its own uses: a CONTRIBUTING file (that the checks are the ones the repo's CI workflow runs; that contributors need not sign, rebase, or write a CHANGELOG entry; that the maintainer may rebase, reword, amend, or squash commits to land them, crediting the contributor as author or co-author; that a PR whose commits land unchanged, or whose topic branch allows maintainer edits and receives the rebased commits, shows as merged, and otherwise as closed with a comment linking the landed commits) and issue forms asking for the project and toolchain versions and a minimal reproduction. A repo adds its own file only where it differs - except issue templates: a repo with any file in its own `.github/ISSUE_TEMPLATE` gets none of the defaults, so it copies every form it keeps. No code of conduct or funding file unless the user asks.
