# Published compatibility

## Public surface

Only surface carries promises. Surface is what the project documents or exports, plus what a consumer must touch to use it:

- Zig library: root-module exports and their types, documented behavior, the values and errors its functions return (including exit codes a framework hands back), `build.zig` module names and options. Adding a member to an exported error set or exhaustive enum, or a field without a default to an exported struct, is breaking: exhaustive `switch` and struct literals stop compiling.
- Lua plugin: documented `require` modules and functions, `setup()` keys and their defaults, commands, `<Plug>` mappings, autocmd events, highlight groups.
- Grammar: node types, field names, aliases, and the tree-sitter ABI the generated parser targets.
- CLI tool: commands, flags, exit codes, machine-readable output, config file format, on-disk state, and the release artifact layout installers read. Stdout of a command meant to be piped or captured (lists, paths) is machine-readable unless documented as human-only.
- Other languages: documented items the ecosystem marks public (Rust `pub` items, Go exported names, a package's `exports`). Python: names in `__all__`; a module without `__all__` exposes its documented names without a leading `_`; a new project defines `__all__`, and adding one that leaves out a documented name is breaking.
- Hosted service: its API (endpoints, fields, status codes, authentication flow).
- A dependency whose types appear in the surface is part of it: bumping it across a breaking change is breaking.

Not surface: undocumented or `_`-prefixed internals, human-facing message wording, help layout, performance, and anything documented as experimental until that mark is removed. Export only what is meant to be supported; an accidental export is surface until a breaking release removes it.

## Classifying a change

- **Breaking:** removes or renames surface; changes documented behavior or a documented default; adds an exhaustive-type member or a defaultless field (above); rejects input that was accepted; changes machine-readable output, exit codes, files other programs read, or a return value. Output (what a tool prints), exit codes (including those a library returns), and files the project itself writes for other programs break even for a fix that matches the docs. Data a library returns or writes to a caller-supplied writer (serialized text included) is a return value: changing it is a fix when the old value contradicted the docs, or the specification the project implements where the docs are silent; a value the docs describe is documented behavior. An internal state format may change without breaking only while older data is still read correctly (see Persisted formats).
- **Fix:** corrects behavior with none of those effects (patch). Record visible effects under "Fixed".
- **0.0.z:** a project at 0.0.z makes its next break 0.1.0, after which the rules above apply.
- **Toolchain range:** raising the minimum takes a minor bump (0.(y+1).0 before 1.0, 0.1.0 from 0.0.z, x.(y+1).0 from 1.0), never a patch, and is not a break for semver (Cargo convention); follow the ecosystem's own rule where it differs (npm: major). Widening the range is an addition (see Additions). Mark a raised minimum's commit `!` where the repo uses conventional subjects - users tracking `main` on the dropped version break on their next update.
- **Additions:** new surface, or a widened range, may take a patch bump before 1.0 (0.y.(z+1)) and need a minor bump from 1.0 (x.(y+1).0).
- **Who decides:** propose any breaking change the user did not ask for, and prefer a route that needs no deprecation (an opt-in flag, a new option or command) when one exists - never a second name for the same thing. A fix that must apply by default (a security limit) has no such route; it is breaking.
- **Marking:** in a repo with conventional commit subjects, every breaking commit carries `!` (`feat!:`, `fix(scope)!:`) - users tracking `main` see it in lazy.nvim, which detects only `^%S+!:`; a release also lists breaks in the CHANGELOG's breaking section and its release notes. "Conventional subjects" means 90% or more of recent subjects, the commit hook's threshold. A repo without them marks breaks in the CHANGELOG and notes only (the hook rejects a `type!:` prefix there). A project without releases uses conventional subjects; moving a repo to them is the user's call - until then, name each break to the user when committing it.
- **Security exception:** a security or data-loss fix that cannot be made without breaking may ship in a patch only with the user's agreement; mark it breaking and say why.
- With a CHANGELOG, every user-visible change gets an entry; a breaking one gets a one-line migration (old -> new). Batch breaking changes into as few releases as practical; a release that already breaks (or adopts a new toolchain) is a good carrier.

## Deprecating a name

Stages: warning, then error, then deletion. Each stage lasts at least one release and at least one month; without releases, at least three months. Unless the user says otherwise, use the earliest dates those minimums allow. Every message names the replacement (or says there is none) and the next stage's date or release. The stages apply even when the user asked for the rename and even when the only known consumer is the user's own repo (that repo still adapts in its pin-bump commit); skipping them needs the user's explicit say-so.

- **Warning stage** (any release; not a break; without releases, a commit not marked `!`): the old name keeps working and warns once per session or run - Lua `vim.deprecate` or `vim.notify` at WARN; a CLI flag, command, or config key on stderr; elsewhere the ecosystem's standard (Python `DeprecationWarning` for APIs and `FutureWarning` to announce a behavior change ahead of its breaking release, Rust `#[deprecated]`, Go `// Deprecated:`, Node `util.deprecate`). A hosted API follows "Support windows" instead.
- **Error stage** (a breaking release; its commit marked `!` where the repo uses conventional subjects): the old name fails with an error naming the replacement. A deprecated `setup()` or config key at this stage is reported at ERROR and ignored; it never aborts startup.
- **Deletion** (any later release; without releases, a later commit not marked `!` - the error stage already broke): remove the stub.
- Unknown `setup()` or config keys warn and show in `:checkhealth` (or the tool's doctor command); they never abort startup.
- **Zig** has no warnings (`@deprecated` is not in 0.16 or 0.17), so it starts at the error stage in the breaking release that renames: `pub const Old = @compileError("Old was renamed to New in 0.7.0; removed in 0.8.0");`. It errors only where used, but `std.testing.refAllDecls` on its namespace trips it - grep for `refAllDecls` and reference that namespace's other declarations explicitly instead.
- **Grammar** node or field renames cannot warn or error. Ship them as breaking: list each rename in the CHANGELOG if kept, and in the commit body where the repo's history uses bodies (in a subject-only repo with no CHANGELOG, in the README Compatibility section). Update the consumer's queries in its pin-bump commit.

## Toolchain range

Declare it (`minimum_zig_version`, README, `engines`, `rust-version`) and test its oldest and newest in CI; without CI, declare only what was tested locally and propose CI to the user. The README claims no more than was tested. Nightly or dev builds may be tested but are not supported.

The range covers at least the ecosystem's floor:

- Zig on a breaking toolchain series (before Zig 1.0, or Zig 1.x before a compatibility promise): the latest stable toolchain series (0.T.x). `minimum_zig_version` is the oldest patch tested. A port proposed and not yet decided, an approved port not yet past its due date, or a recorded skip, wait, or block (see "Support windows") keeps main compliant. Zig once compatible: the latest two minors released under the promise (one until a second exists).
- Neovim: the current stable minor and the previous one.
- Grammars: the ABI the oldest supported consumer runtime loads (Neovim 0.10 loads up to ABI 14; 0.11 and 0.12 load 15). Generate with an explicit `--abi N` and pin the tree-sitter CLI version that generates `parser.c`.
- Others: Go: the two latest releases. Python: SPEC 0, for Python and core dependencies. Node: active and maintenance LTS. Rust: an MSRV no newer than the newest stable release at least 6 months old. Any other toolchain: the ecosystem's library convention where one is documented, otherwise every release its vendor still supports, and at least the latest two.

On a breaking toolchain (see "Support windows"), a new toolchain series is a port, proposed as that section says; a patch release within main's toolchain series is not, and a declared range spanning two toolchain series is proposed for narrowing, which opens what a port would for that kind. On a compatible one, CI's newest slot follows the current stable without a proposal and the README states the range as "X+"; that is not a range change. Propose raising the minimum only when a change needs a newer release, and dropping a version below the floor only when it needs compat code, for every affected project of the user's at once (ask the user if you cannot list them); list a raised minimum in the CHANGELOG's breaking section. Never raise or drop a version yourself. A new project starts at the floor unless the user chooses wider. Until the user decides, the declared range stands and is compliant (a breaking-toolchain range already spanning two toolchain series included); a decision to keep a version below the floor is recorded in the README and stands until a change needs that version dropped. A change that needs a toolchain newer than the floor allows waits, or is the user's call. On a compatible toolchain, a range wider than the floor is allowed when the user chose it, CI covers it, and its code stays isolated; a range already declared counts as chosen. "X+" in a README is accurate when CI tests X and the current stable. Never remove in-range compat code as cleanup.

## Multiple versions

- Inside the range, the default branch serves every version. Conditional code lives in one compat module per artifact (plus the build script where the build API itself differs). Key it on the version when the version decides (`vim.fn.has("nvim-0.12")`), on a feature test otherwise (`@hasDecl(std.Build.Step.Run, "addPassthruArgs")`, `vim.uv or vim.loop`, `has("win32")`), with a one-line marker naming the version it serves and its deletion trigger (the release the user chose, or "when <version> leaves the range" until they choose).
- If a declared version cannot be served from one compat module, the range is too wide: propose narrowing to the user and keep supporting the version until they decide.
- Outside main's declared range, the last release supporting a version stays tagged (a project without releases gets a version branch if the user approves one; otherwise the pin table names the last commit). Fixes to older versions follow "Support windows"; creating any remote branch for them needs the user's yes.

## Support windows

Support windows cover what adopters cannot control: a toolchain they cannot move off, a dependency they cannot upgrade until others move, or a release they pinned. They cost work only when a fix exists. The research behind every number is in `references/evidence.md`; apply these rules rather than redoing it, and reopen a rule only on a trigger listed there or when the user asks. Every outward-facing action below - branch, tag, release, deploy, push, merge, fork, PR or issue creation, state change, or comment, advisory, README or `SECURITY.md` publication - needs the user's yes. A case is open only when no rule decides it or two rules conflict (name both in the proposal). A judgment a definition governs (security, data loss, toolchain class) or an ordinary judgment (whether a fix is user-visible, whether it ports without redesign) is not open - make the judgment and name it in the proposal. For an open case, propose to the user the reading that keeps the most adopter protection among those that add no tier, window, length, deadline, branch, or outward action beyond what the rules give the nearest comparable case (between equally near cases, the cheaper reading). The user's answer decides: record it as "decided by the user <date>: ..." (for a vulnerability not yet public, in its draft advisory). An unanswered proposal is recorded as "proposed <date>", decides nothing, leaves every clock running, and is raised again the next time the project is worked on.

**Terms.**
- **main:** the default branch, whatever its name.
- **Series:** the project's releases sharing a minor before 1.0 (0.N.x) or a major from 1.0 (N.x). A bare "1.0" means the project's own.
- **Toolchain series:** a breaking toolchain's releases sharing a minor (Zig 0.T.x); always written "toolchain series".
- **Line:** the maintenance branch a port release opens (`zig-<toolchain series>`, as `zig-0.16`), in a project following the library rules (see By kind).
- **Current series:** the series of the highest version published; without releases, main.
- **Series branch:** `v0.N.x`, `vN.x`, or from 1.0 `vN.M.x` for a superseded minor (still called a series branch); cut from the last tag when a fix needs it, or at a port's base.
- **Version branch:** in a project without releases (other than a grammar or a hosted service), `<toolchain>-<version>` (`nvim-0.11`, `zig-0.16`) at the last commit whose CI passed on a version that left main; releasing on it means landing a commit on it (through CI in a repo with the `repo-workflow` setup; otherwise merging a PR into it after the PR's CI passes).
- **Window:** (the heading "Support windows" covers lines, windows, and version branches alike) a promise to superseded releases: security and data-loss fixes (below), or for a hosted service, continued service of the old behavior (By kind). It exists from the release that opens it, whether or not a branch exists yet. Lines and version branches likewise have their tiers whether or not the branch exists yet, and until it does the pin table names the last tag or commit; a line or branch the user declines before the release that would open its tiers opens none (and a declined line gets no base, the port giving the superseded window instead, as for a tool): the README records the decline, and the pin table names the last tag or commit with its window's end date, or as unsupported where none applies. Declining one whose tiers are already published is an early end (see Decisions).
- **Security** and **data loss:** as defined under Communication.
- **Merged / landed:** a commit reaching a branch; in a repo with the `repo-workflow` setup, only by fast-forward through CI.
- **Tier:** a fix scope: non-breaking fixes that port without redesign, or security and data-loss fixes. **Frozen:** past the last tier; branch and tags stay, nothing merges.
- **Deadlines:** a "within N days" or "due" date is when the work is ready and its release proposed; releasing still needs the user's yes. A backport's 30 days cover both merging it and proposing its release.
- **Dates** are UTC: the publication date of the release that opens a line or window (for a version branch, the date the commit that stopped serving that version reached main, recorded in the README with that change), plus calendar months, clamped to the month's end. A tier includes its end date.

**State in the README; overdue items when found.** The README's Compatibility section records each port as "port to 0.T: proposed <date>", "approved <date>, due <date>", "blocked by <issue> since <date>, review <date>" (a block is a wait, re-proposed every 30 days), "waiting on <dependency> since <date>, review <date>", "skipped", or "released <version> <date>" (replaced when the next port is proposed); states combine ("approved <date>; waiting on <dependency> since <date>"), and the due date is written once known. It also records each decision to keep a version below the floor, each release or backport the user declined (final; a backport declined within a published tier is an immediate early end for that fix alone, with no 90-day notice - say it breaks the published promise, and with the user's explicit yes announce it as unfixed with a mitigation and the pin-table warning for a security or data-loss fix, in the advisory first while the vulnerability is not yet public) or deferred (with the date the user names to raise it again), each scheduled breaking release, and each answer under the open-case rule. Commit a proposal or decision note to main, on its own, when it is made; push or land it with the next push or landing on main (naming it when asking), or propose landing it alone (pushing it, without the `repo-workflow` setup) if none is planned. An early-end or retirement notice is committed and, with the user's yes, landed (pushed, without the setup) when the user approves it; it states its end date, at least 90 days after that landing unless the user explicitly chose a shorter notice. Security work on a vulnerability not yet public is never recorded in the README; its state lives in the draft security advisory. Agents act only in sessions, and the `upkeep` report (`repo-workflow`) only reports: whenever you work on a project, propose anything overdue at once, skipping what the README records as decided - main on an older breaking toolchain series with no port note (for Zig, compare with ziglang.org/download/index.json), an approved port past its due date, a merged user-visible fix unreleased past its release deadline on main, on the current series' series branch, or on a branch whose tier covers it, a backport not proposed, a version below the floor carrying compat code with no recorded decision, a wait or a deferred item past its review or raise-again date, a security report or draft advisory past its deadline (`gh api 'repos/{owner}/{repo}/security-advisories?state=triage'` and `?state=draft`; inside a sandbox without `gh`, queue the check for the host session). If a port is first proposed more than 14 days after the stable release, every clock that counts from the stable release counts from the proposal instead. A missed port due date is recorded when found.

**Classify the toolchain.** Go, Rust, Python, Node, and Neovim are compatible; Zig is breaking until its release notes state a compatibility promise (expected at Zig 1.0). Any other toolchain is compatible if every release keeps code written for the previous release working, removing anything only after a deprecation period of at least one release; otherwise breaking.

- **Compatible:** support lives in main, within the range from "Toolchain range". A toolchain move opens no line.
- **Breaking:** main targets one toolchain series, the latest stable it has been ported to, never a dev build; `minimum_zig_version` (or its equivalent) names it, and each line declares its own. Main never takes on a second toolchain series; a declared range already spanning two stands until the user decides (see "Toolchain range").

**Porting main to a new breaking toolchain series:**
- Propose it within 14 days of its stable release, for every affected project of the user's at once (ask the user if you cannot list them), listing each surface change the port forces. Release it within 30 days of the later of approval and the last dependency's port (its release, or for a dependency without releases a default-branch commit that builds and passes its tests on the new toolchain series). If a dependency has not ported within 60 days of the stable release, propose forking, replacing, skipping the toolchain series, or waiting. Re-propose any wait every 30 days; if a newer toolchain series ships during a wait, the port is re-proposed for it and the passed-over one goes into the pin table.
- A toolchain regression that breaks the project's build or tests blocks the port unless a workaround in the project's own code exists; propose the workaround or waiting. A fixing patch restarts the 30 days, whenever it ships before a skip is decided. If none ships within 60 days of the stable release, propose skipping that toolchain series; a skip stands, and the next port goes to the next toolchain series.
- Base: after approval and before the port releases, publish the last release for the old toolchain series on the branch that will carry it - the line in a library, the series branch in other kinds with releases - created with the user's yes. If main holds no unreleased breaks and no raised minimum, release main as it stands (a patch, or from 1.0 a minor for unreleased additions); if the last tag already holds every merged non-breaking fix, that tag is the base. Otherwise cut a patch from the last tag with every merged non-breaking fix cherry-picked; the breaks ship in the port. The base opens no window; the branch's tiers start at the port release.
- Moving to the new toolchain series is a minor bump and not itself a break. Every other surface change in the port release is a break under "Classifying a change", which makes the port a major release when the previous release is 1.0 or later. A name the new toolchain series makes impossible to keep becomes an error-stage stub (Zig: `@compileError` naming the migration and the release that deletes it; see the `refAllDecls` note under "Deprecating a name"), deleted no earlier than one release and one month after the port release (three months without releases). A removed build option keeps its `b.option` and fails at configure time with the migration, under the same lifetime. A forced removal that cannot be stubbed (a field, an enum or error-set member) and a changed type or signature have no stage. List each forced change in the port proposal and in the CHANGELOG with its migration; every other removal follows the deprecation stages. Mark the commit `!` where the repo uses conventional subjects.
- Port PRs are welcome and land at the port. A PR for a dev build stays a draft until the stable release, then lands as a straight port without version-conditional code; if the contributor has not replied within 30 days after the stable release, finish it and ask the user about a `Co-authored-by:` trailer.
- The port to the toolchain's first release under a compatibility promise follows these steps and, in a library, opens a line for the toolchain series it leaves; after it, the project follows the compatible rules, and open lines keep their published dates.

**Maintenance line** (`zig-0.T`), opened by the port release, in a library with releases:
- Its first release is the base; later releases are patches of it. An existing series branch for the base's series ends there and its fixes continue on the line.
- Non-breaking fixes that port without redesign until 6 months after the port release; a fix not ported is listed in the README's entry for the line and in its next release notes (without releases, the README only). If a newer line opens sooner, this tier ends 3 months after the port release or at the newer line's opening, whichever is later. Publish both dates when the line opens: "fixes through <6-month date> (unported fixes listed); through <3-month date> at the earliest if a newer line opens".
- Security and data-loss fixes until 12 months after the port release; then frozen.
- A toolchain series main never adopted gets no line; the pin table lists it as "unsupported; use 0.T with vX.Y.Z", naming the nearest supported toolchain series on each side that exists.
- Usually main plus one or two lines are open; there is no cap, since every port opens its line.

**Superseded releases** (any project with releases): each release that breaks surface or raises a compatible toolchain's minimum gives the releases it supersedes security and data-loss fixes - the previous series, except that from 1.0 a raised minimum, or a binary tool's port without other breaks, supersedes only the previous minor. The window is 3 months when those releases are 0.x, 6 when they are N.x. Fixes ship as patches from a series branch. Each window keeps its own dates and windows may overlap; batch breaks so that usually one is open. In a library, a port opens a line instead; a patch shipped under the security exception opens nothing. While main holds unreleased breaks, a fix for the current series ships as a patch from its series branch, which later serves that series' window.

**By kind:**
- Library with releases: all of the above. A project that exports a library surface follows the library rules even if it also ships binaries, and any project with releases not listed here follows them too.
- CLI tool or application shipped as binaries: as a library, but a port opens no line; it gives the releases it supersedes the superseded window instead (see "Superseded releases"), for packagers building from source. Changing the toolchain the binaries build with is not a range change for binary users; porting is still proposed and the user's. The README names the build toolchain; packagers on older toolchains use the pin table. One installed from source through the ecosystem's package tool (`cargo install`, `go install`, `pip`, `npm`) also keeps the library range, stated beside the build toolchain. When a security or data-loss defect in the toolchain or a bundled dependency affects a shipped binary, propose rebuilding and releasing a patch of the current release and of every series branch whose security and data-loss tier is open; where the toolchain fix exists only in a newer release, say so in the advisory or release notes instead.
- Project without releases (any project without tags: plugins, libraries, tools; grammars and hosted services below): the declared range, at least the floor. When a version leaves main, propose a version branch. After a breaking-toolchain port it gets the tiers the same kind with releases would get at 0.x (a library's line tiers; a tool's 3-month security and data-loss tier); after a dropped compatible version it takes security and data-loss fixes for 3 months; then it is frozen. The pin table names it. For a library, propose tagging releases once, with the first version-branch proposal, noting that each later breaking release then opens a window; record a decline.
- Plugin: a load-time check of the oldest supported version reports at ERROR, names what to pin for the running version (the version branch or, before it exists, the last commit; or the series's latest tag as a `v0.N.*`, `vN.*`, or `vN.M.*` constraint so later patches fit) or says none exists, and the plugin registers nothing further; it never aborts startup and never blocks newer or nightly versions. The check is range enforcement, not compat code: it moves with the range and carries no deletion marker. A plugin with releases follows the library rules plus this check.
- Grammar: the ABI rule under "Toolchain range"; no lines. Without releases it gets no version branch; consumers pin a revision, and the pin table names the last revision generated for each dropped ABI. A grammar with releases also follows "Superseded releases".
- Hosted service: nothing to pin, so no lines. A breaking API change is announced on its first day with `Deprecation` and `Sunset` response headers and a changelog entry, and the old behavior (field, endpoint, or version) keeps being served for 3 months, 6 once the user declares the API stable in its docs. This is the service's window: its dates and the early-end notice apply (published in its API docs and `Sunset` headers), deploying is its release, and its API docs hold the Compatibility section; it needs no `SECURITY.md` table, and "Superseded releases" does not apply. A security or data-loss fix that must change the old API applies at once with the user's agreement and is announced in the changelog.

**Fixes:**
- A fix lands on main first (a security fix not yet public: as the private procedure below says), with its test, and its backport - to every line and branch whose tier covers it, and to the current series' series branch while main holds unreleased breaks - is proposed the same day, naming the integration method (cherry-pick). A backport is due 30 days after the fix lands; a security or data-loss backport ships with its 7-day release. Only a non-breaking fix on a line, or on a version branch with a line's tiers, may be listed as not ported, when it does not port without redesign; propose that listing to the user. A security or data-loss fix that does not port without redesign is proposed as a redesign or as unfixed on that line or branch; if unfixed, the advisory or release notes (without releases, the README) name it, a mitigation, and the pin to move to.
- A security report not yet public: propose that day accepting it (a private vulnerability report) or opening a draft repository advisory; keep the report date and any working notes in the draft, removed before publication. First create, publicly and with the user's yes, any line, series branch, or version branch the fix needs (`repo-workflow`, "Creating a release branch"). Prepare the fix privately - in the advisory's temporary private fork for review with the reporter (it runs no CI), or locally - for main, the current series' series branch while main holds unreleased breaks (not for a breaking fix that goes to main only), and every line and branch whose tier covers the fix; test each locally, or with the user's yes in a private repository with CI. By 30 days after the report, or a later disclosure date the user agrees with the reporter (recorded in the draft): drop any backport not ready (it continues under the public procedure) and land the rest - in a repo with the `repo-workflow` setup through CI, one landing yes naming every target, in parallel, each as its `ci-ok` passes, the fork's merge button never used; otherwise merged at once from the advisory (on a host without private forks, a private repository), with the merge method confirmed with the user, CI running after the merge. Nothing lands before main's fix is ready; if it is not ready by the date, propose a new date agreed with the reporter, or publishing the advisory with the vulnerability unfixed and a mitigation. Release each landed branch except main while it holds unreleased breaks; a branch whose CI fails is fixed and landed again (without the setup, fixed forward). Publish the advisory once each branch that releases has released or been failing for 2 days; it names a branch still failing as fixed in a coming patch and a dropped backport as coming under the public procedure. If the vulnerability becomes public first, the main-first hold ends: land what is ready at once and continue under the public procedure.
- The public procedure - for a vulnerability already public, a public toolchain or dependency fix, and a backport that missed the private landing: the fix lands on main as soon as it is ready and each backport releases within 7 days of the vulnerability becoming public (for a backport that missed the private landing, 7 days after the advisory), never waiting for main, or, if it needs a redesign, is proposed as a redesign (deferred, with the date the user names) or as unfixed. An advisory not yet published follows the current series' release.
- Propose a release of each merged user-visible fix within 30 days of its merge, and of a security or data-loss fix within 7 days. A user-visible fix that is not a security or data-loss fix may wait for a breaking release the user has scheduled for no later than 60 days after the merge; a security or data-loss fix is proposed the day it is found, is never held for a scheduled release (one that can ship only by breaking follows the declined-exception rule below), and ships as a patch from the series branch if main holds breaks. Features land on main only.
- A fix that "Classifying a change" makes breaking goes to main only, unless it is a security or data-loss fix the user agrees to ship under the security exception; without agreement it ships in a breaking release proposed within 7 days of the fix being ready (for a fix not yet public, of its merge), and the advisory follows that release, naming superseded releases unfixed with a mitigation.
- A bug present only on a line or branch is fixed there, with its test, after checking main, if its tier covers it.
- Recommend declining, with thanks, a fix outside the tier of the line or branch it is offered to; point to the newest line or branch whose tier covers the fix, or main, and to the pin table. Contributors are never asked to backport; a backport within the tier is welcome. The README names which branch takes which PR.
- A security or data-loss fix that must reject input that was accepted (a depth, size, or time limit on hostile input, or refusing a write it would corrupt) is breaking: recommend that the user ship it in a patch under the security exception, for a limit on hostile input, with the limit configurable and its default far above legitimate use (from 1.0 the option is an addition carried in the same patch under the exception).
- Propose a GitHub security advisory for each security fix, and at a project's first release (without releases, its first publication), or the first time you work in a published project that lacks them, propose enabling private vulnerability reporting and a minimal `SECURITY.md` once, and record the answer in the README's Compatibility section. Announce a data-loss fix under a "Data loss" heading in the release notes (without releases, in the README's Compatibility section and the fixing commit's body) and with the pin-table warning.

**Communication:**
- The README's `## Compatibility` section is the source: main's toolchain series or range; the versioning rule; each port note and recorded decision; each open line and window with its series branch or version branch once one exists, its base or commit, and its dates per tier; unported fixes per line; which branch takes which PR; for a binary tool, the build toolchain; and a pin table "using 0.T? pin vX.Y.Z" covering every breaking toolchain series the project supported and every version dropped from a compatible range (a version branch or commit where there are no releases), with a warning beside any pin with a known security or data-loss defect.
- `SECURITY.md` (proposed at the first release; see Fixes) says how to report privately and what counts for the project; when the first line, window, or version branch opens it gains GitHub's supported-versions table and a link to the README for dates. Security: a defect that lets hostile input or an unauthorized party read, write, or run anything beyond what the documented behavior permits - memory-safety faults, injection, path traversal, authentication or authorization bypass, exposure of secrets - or that causes unbounded time, memory, or recursion on hostile input. Data loss: stored data destroyed, corrupted, or silently written wrong by the project itself (a file it opens, including one the operation did not name; a database or state it updates), or by output it documents as a storage format with a round-trip guarantee; any other wrong result returned to the caller is a bug, not data loss. A wrong error message is neither.
- Dates are fixed when published, shortened only as the line rule states or by an announced early end; the README and `SECURITY.md` say that dates may end earlier with 90 days' notice. A tier's end needs no same-day edit; the next commit or release updates the tables.

**Tooling:** in a repo with the `repo-workflow` setup, every line, series branch, and version branch is in the branch ruleset and is created and receives commits only through CI; otherwise the first commit on a new one makes its CI trigger on that branch, and nothing else lands or is tagged there until that CI passes. Each pins its own toolchain, and any release workflow on it marks Latest only when the release is the highest version published so far. In every project with releases, only the highest version published so far is marked Latest, from whichever branch it ships (a base, or a series-branch patch while main holds breaks, can be); a patch below the highest never is, so installers that follow Latest never move backwards.

**Frozen:** you may propose reopening a frozen line or branch (not a retired project's) for one security or data-loss fix that ports cleanly; it refreezes after that release.

**Decisions:** the user approves each line with its port and each series or version branch when it is created; propose each backport, release, push, and tag (see the opening paragraph for every action needing a yes). Each port, dropping any toolchain release, lengthening a line's, window's, or version branch's tier, ending one early, and retiring a project are the user's. An early end or retirement is announced in the README and `SECURITY.md` at least 90 days ahead. If the user wants an earlier end, say that it breaks the published promise and needs their explicit yes; then publish the actual end date in both before it takes effect. Until the end date the affected lines and branches keep their current tiers, and on that date retirement freezes them all.

## Persisted and published formats

- Every persisted format carries a format version from its first release. Existing data without one is version 1; the next format change adds the field.
- Older data, in order of preference: read it correctly (the reader stays while that format is supported); or keep it apart (versioned path or marker), never read it, and tell the user once what to do with it; or refuse with a message naming the upgrade step. Deleting old data is acceptable only when the message says so and nothing is lost silently. Before 1.0, migration code is optional; detection, the message, and the documented step are not. Which option to use, and when to stop reading an old format, is the user's decision; the reader names the release they chose.
- Newer data: refuse ("written by a newer <tool>; upgrade").
- A script that accepts an old release as input (installer, updater) handles that release's published layout for as long as it accepts that version, or refuses the version by name. Stopping acceptance of an old release is the user's decision, as is the installer release that does it; the code names that release.

## Releases

- Never move or delete a published tag: Zig consumers pin a content hash. Fix a bad release with a new patch, say so in the notes, and propose the ecosystem's retraction where one exists (Go `retract`, `cargo yank`; Zig has none, so the release notes carry the warning); publishing, yanking, and retracting each need the user's yes. Tagging follows the `release-discipline` skill.
- 1.0 is the user's decision, independent of the toolchain's own version.

## Consumers

A published project consuming another published project pins a tag or revision it was tested with and bumps the pin in the same commit that adapts to the new version; it never tracks a dependency's moving tip. The user's own consumer repos are callers you control: adapt them, rather than keeping compatibility code for them. A consumer that exposes a dependency's surface to its own users (a plugin whose users write queries against its grammar) inherits that dependency's breaks: mark its pin-bump commit or release as breaking. A personal config follows its lockfile.

## README

A `## Compatibility` section holding everything "Support windows" lists under Communication; for a project with nothing open, that is at least main's range, the versioning rule, any pin table, and (for projects without releases that use conventional subjects) that breaking commits are marked with `!` in the subject. For a hosted service, its API docs hold it. Create it in the first commit that records anything and update it as "Support windows" says under "State in the README", or when the user asks. Main's README is the source; other branches' READMEs need not follow.

## Outside contributions

Review with the `review-pull-request` skill. Recommend declining version-conditional code for a version outside main's declared range, citing the README's Compatibility section, unless the user widens the range (compatible toolchains only); point the contributor to the line, series branch, or version branch that takes the change, if one does. Post or close only with the user's yes. Take the substance (a port, a fix) where useful, and ask the user whether to credit the contributor with a `Co-authored-by:` trailer.
